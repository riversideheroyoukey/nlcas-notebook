# Practice-loop scenario S-l: a single-mode squeezed state (Bogoliubov transformation)

> Run 2026-08-04.  The squeeze transformation of a single bosonic mode, built entirely from the
> **general L-1 (linear basis change) operations**: check that it preserves the canonical commutator,
> then compute the photon number of the squeezed vacuum.

**Backend:** Julia (QuantumAlgebra.jl) / **Domain:** quantum optics.

### The physics

The squeeze operator $S(r)=\exp\left[\tfrac{r}{2}(a^2-a^{\dagger2})\right]$ induces the Bogoliubov
transformation

$$b = S^\dagger a S = a\cosh r - a^\dagger \sinh r,\qquad
b^\dagger = a^\dagger\cosh r - a\sinh r$$

**Two things to check:**

1. the transformation preserves the canonical commutator (i.e. it is physically allowed):
   $[b,b^\dagger]=\cosh^2 r-\sinh^2 r=1$
2. the photon number in the squeezed vacuum (the $b$ vacuum) is
   $\langle a^\dagger a\rangle=\sinh^2 r$ — there are photons in a vacuum, which is what squeezing is

### Building it from general operations (the point of this scenario)

No dedicated "squeeze operator" operation is added.  L-1 and the general operations are enough:

1. declare $a$ as "the annihilation operator for photon" (`models/particles.json` resolves the name)
2. declare $b$ as a plain "boson operator" — it is not a named particle species
3. register the forward transformation **with both components**, in H-1 equation form
   (the dagger is not auto-generated by design)
4. take $[b,b^\dagger]$ with `commutator` and reduce it to $1$ with `simplify`
5. express $a,a^\dagger$ in terms of $b,b^\dagger$ with `build_inverse_transform`
6. substitute into the number operator $a^\dagger a$ and take `vacuum_expectation`

This is the **same skeleton as S-c** (BCS) — only the coefficients differ, $(u,v)$ there and
$(\cosh r,\sinh r)$ here.  That the same general operations carry a different piece of physics is
itself part of what this checks.

## What this run found

**This scenario turned up two display defects.  One of them had already shipped.**

| # | Symptom | Cause | Fix |
|---|---|---|---|
| 1 | the inverse-transform result displays as `\mathrm{b'}\left( 1 \right)` — CAS spelling leaking out | Julia's Latexify hands a bare operator name back **wrapped**, and the display bridge did not know that shape, so it passed through untouched.  **It was in the shipped S-c example too**: `\mathrm{g'}(k,u)` sat in the same timeline as a correctly rendered `{c}_{k}^{\dagger}` that came from QuantumAlgebra's own latex — one operator, three spellings | the wrapping is a backend's habit, so the backend declares it (`_DISPLAY_NAME_WRAPPERS`, Backend Encapsulation Rule).  Maxima does not wrap, so nothing changes there |
| 2 | **the dagger was silently dropped**: `b'(k) b(k)` → `b_{k} b_{k}`, a number operator displayed as something else | the adjoint marks were counted from the REGISTERED NAME, and operators are registered under the bare base (`b`), so the count was always 0; the `'` in the text was consumed by the pattern but never captured | count the marks found in the text as well |

**Defect 2 was unreachable at the time** — a differential check over every generated Julia example
found 0 collapsed displays, because QuantumAlgebra returns subscript forms and Latexify returns
`\mathrm{}`-wrapped ones, and neither matched the pattern.  **But fixing defect 1 is exactly what
would have made it reachable**, so both were fixed together.  A latent defect is not one you can
leave alone while changing the thing that gates it.

**The inverse transform skips an E-number** (at the time: it registered E4 and E6, leaving E5 empty).
Both values are there, so this is not a correctness problem, but the researcher sees a hole in the
numbering.  Filed as INTERNAL-INTERMEDIATE-EID-GAP in open_items.
**[Resolved 2026-08-06]** The first solution row is now registered straight into the pre-allocated
slot, so there is no gap, and the numbers in the tables above were shifted to match
(E6→E5, E8→E7, E9→E8, E10→E9).  Closing a gap can only move the numbers after it, so any script
that wrote E-numbers down needs rewriting — this scenario is the worked example of that, and the
breakage only became visible by running the generator rather than checking by hand.

**A third defect — a non-existent E-number became a symbol.**  While building this scenario an
E-number was misread and `In E8, substitute E5 for a(1) …` was written (numbers as they were
then; E5 being the empty slot).
Instead of failing, **`a^\dagger(1) a(1) = E5^2` was registered as a success.**  The backend expander
replaces every string that looks like `^E\d+$` with that expression's text, but an unknown number
does not get replaced and is then parsed as an ordinary **symbol**; the validator was not treating
`rhs` as an expression-reference field.  **Fixed 2026-08-04** by widening the check to the same shapes
the expander reaches into (`rhs`, and nested inside `op_rules`).  The invariant: **whatever the
expander will look up, the validator must have checked exists.**

**"as the annihilation operator for a quasiparticle" does not work** (same as S-c).  The particle
dictionary lists proper names, so a generic operator with no particle species is declared as
"a boson operator".

**Verified:** 2026-08-04 (real Julia, ST-1 through ST-5).
