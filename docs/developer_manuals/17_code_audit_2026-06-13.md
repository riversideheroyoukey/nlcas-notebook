## 1. 検出事項（重大度順）

重大度: **高**=機能・正しさに影響しうる / **中**=規則違反・保守性 / **低**=軽微・様式

### 中-1. バックエンドカプセル化漏れ（engine.py）— ✅ 解消済み (2026-06-13)

> **対応済み:** `BackendHandler` に能力フック（`binds_symbol_definitions`・`init_coordinate_system`・`prepare_sympy_wick_inputs`・`reserved_coord_vars`・`coord_component_suffixes`）を追加し、engine.py から `isinstance`/`primary_backend ==` 分岐と Maxima/Julia モジュール直接 import をすべて排除。詳細は open_items.md AUD-2。以下は記録として残す。


CLAUDE.md「Backend Encapsulation Rule」は shared 層での `if engine.primary_backend == "..."` や `isinstance(...BackendHandler)` を明示的に anti-pattern としている。`notebook/engine.py`（shared 層）に以下の分岐が残る:

| 箇所 | 内容 |
|---|---|
| engine.py:501, 504, 568 | `primary_backend != "maxima"` / `isinstance(MaximaBackendHandler)`（座標系バインド）|
| engine.py:848 | `primary_backend == "maxima"`（CAS バインドのスキップ判定）|
| engine.py:1716 | `isinstance(JuliaBackendHandler)` ＋ Julia 専用ジェネレータを engine 内で直接 import |

注: engine.py:1883/2054/2684 の `primary_backend` 使用は文字列パラメータとしての受け渡し（validator・make_backend）で、分岐ではないため違反ではない。

**推奨対応:** 各分岐を `BackendHandler` の抽象メソッド（例: `bind_coordinate_system()`, `collect_statistics_json()`）に押し出し、サブクラスで override する。特に 1716 の Julia ジェネレータ直接 import は、`_handler` 経由のメソッド呼び出しに置換すべき。規模: 中。

### 中-2. 巨大モジュール（god object）— ✅ 実質完了 (2026-06-13)

> **対応済み:** Stage 1（engine→lhs_formatting）・2a（julia→julia_handler_common）・2b（julia 4 mixin）・Stage 3（engine の history／persistence 2 mixin）を実施。**julia_backend_handler.py 3,905→1,202 行、engine.py 3,367→2,263 行**（計 8 新モジュール）。残る `run_operation` 周辺はエンジンの中核で分割しても関心分離にならないため任意・先送り。詳細は open_items.md AUD-4。


| ファイル | 行数 | 構造 |
|---|---|---|
| `notebook/runtime/julia_backend_handler.py` | 3,898 | 1 クラス・115 メソッド |
| `notebook/engine.py` | 3,367 | `NotebookEngine` 1 クラス・69 メソッド |

CLAUDE.md「Coding Style: Prefer small modules」に反する。両者とも責務が広く、変更時の影響範囲把握が困難。今回のフェルミ面バグ（演算子誤認横取り・代入経路）も、`julia_backend_handler.py` 内で代入ルーティングが複数メソッドに分散していたことが調査を長引かせた一因。

**推奨対応:** 機能境界での分割。julia_backend_handler は「代入系」「微分・積分系」「演算子定義系」「LaTeX 表示系」などに、engine は「式登録」「操作実行」「来歴・分岐」「save/load」などにモジュール分割を検討。規模: 大（段階的に）。

### 中-3. 広範な例外握りつぶし — ✅ 対応済み (2026-06-13)

> **対応済み:** ルーティング・実行・履歴整合に関わる握りつぶし 7 箇所にログを追加（制御フロー不変）。各ファイルにモジュールロガーを追加。詳細は open_items.md AUD-3。


`except Exception` / 型付き broad catch が本番コードに 86 箇所。`bare except:`（型なし）は 0 件で、その点は健全。しかし今回のセッションで、代入が**エラーも出さず無反応**になったバグ（`_maybe_operator_identity` 誤横取り）の調査で、try/catch が症状を隠す危険性が実証された（一時的に入れた `try Symbolics.substitute catch` を、エラーを伝播させるため `if isa QuExpr` 分岐に置換して解決）。

**推奨対応:** 全件の機械的修正は不要だが、特に「ルーティング判定」「代入・solve の実行経路」での broad catch は、握りつぶしでなくログ＋再送出に倒すか、捕捉する例外型を具体化する方針が望ましい。規模: 中（個別判断）。

### 低-1. フロント／バック並行ロジックの同期保守リスク — ✅ 対応済み (2026-06-13)

> **対応済み:** `backend_handler.py` step 7 と `notebook_main.js` prepareLaTeX の sqrt 変換に、互いを指す相互参照コメント（「両コピーを同期せよ」）を追加。


`sqrt(x)→\sqrt{x}` 変換が `backend_handler.py:602-603`（Python）と `notebook_main.js:119-120`（JS）に**同一ロジックで二重実装**されている。今回 `(?<!\\)` ガードを両方に入れたが、片方だけ修正すると表示バグが再発する。バックエンド出力とフロント表示の両方を通るため重複自体は不可避だが、**片方を変えたら必ず両方**という不文律はテストで担保されていない。

**推奨対応:** 変換仕様を 1 箇所（docs かコメント）に明記し、相互参照コメントを両ファイルに付す。規模: 小。

### 低-2. 直近変更のテスト網羅ギャップ — ✅ 対応済み (2026-06-13)

- `_bump_same_var_derivative`（高階微分 LHS 畳み込み）は**単体テストのみ**（test_derivative_lhs_collapse.py）。`engine.run_operation("differentiate", …)` を経た**統合テスト**がない。来歴フィールド（quantity_name 欠落時のフォールバック経路）の実地動作は手動確認に留まる。

**推奨対応:** engine 経由の differentiate 統合テスト（order=2・導関数の再微分）を 1〜2 件追加。規模: 小。
