## 2. 設計判断1：SymPy を `.venv` に入れない

open_items の F-9 は `sympy.physics.wigner` 連携を想定していた。**入れなかった。**

- アプリ venv に sympy は無い。第２量子化の「SymPy 経路」は **Julia の中の SymPy.jl**
  （PyCall 経由の別 Python）であり、Python 側の依存ではない。
- `.venv` に sympy を入れると「バックエンド非依存の第三の記号計算エンジン」が常時
  手に入る。魅力的だが代償が大きい：
  1. **正準形の二重化** — Maxima canonical ↔ sympy 式の往復ブリッジが、Maxima/Julia
     アダプタと同格の保守物として増える。
  2. **SymPy が2つになる** — Julia 側 Conda の 1.14 と `.venv` 側で版が割れると、
     「同じ操作なのにセッションによって結果の形が違う」が起こる。再現性上これは最悪。
  3. **逃げ道になる** — 「Maxima ができない → sympy」が常に可能になると、Core
     Principle #6（バックエンド固定・自動フォールバック禁止）が空文化する。
- そして F-9 には**そもそも不要**だった。CG・3j/6j/9j はすべて階乗の閉形式（Racah）で、
  厳密に自前計算できる。`spin_algebra.py` が「SymPy 非依存の自己完結カーネル」で
  スピン代数を実装した前例と同じ筋。

**将来 sympy を入れるとしたら**（BP-2 の留数・部分分数、F-12 量子化学などが実際に
効いてきた時）、アドホックな呼び出しではなく専用アダプタ＋出自表示付きで、かつ
**Julia 側と同一バージョンにピン留め**して導入すること。

## 3. 設計判断2：厳密数の表現（`Surd`）

値はすべて `Σ_d c_d √d`（`c_d` は有理数、`d` は平方因子を持たない正整数）で保持する。
これが加算と乗算について閉じていることが、9j（6j 3個の積の**和**）を浮動小数に落と
さずに扱える理由。

厳密性を安く保つ2つの事実：

1. **平方根の中身は素因数指数のまま作る。** 階乗は Legendre の公式で素因数指数に
   分解し、平方根は各指数を `divmod(e, 2)` で「偶数部→外、奇数部→中」に割る。
   巨大整数の素因数分解は一度も行わない。
2. **平方因子除去は gcd で済む。** 平方因子を持たない `a, b` の積は
   `√a·√b = g·√((a/g)(b/g))`（`g = gcd(a,b)`）。因数分解不要。

### 実装中に踏んだ罠（`_phase`）

Python の `(-1) ** -2` は **`1.0`（float）** を返す。3j の位相 `(-1)^(j1-j2-m3)` の
指数は普通に負になるため、これが係数に混入して `1/3` が
`6004799503160661/2**54` に化けた（sympy 照合で発覚）。

対策は2段構え：
- `_phase(n)` を `-1 if n % 2 else 1` で定義し、位相計算はすべてこれを経由する。
- `Surd` の係数生成を `_exact()` に通し、**float は例外にする**。同種のバグが
  「もっともらしい厳密数」として素通りすることが二度と起きない。

## 4. 設計判断3：CAS を呼ばない／バックエンドに依存しない

角運動量代数はバックエンドの仕事ではない。すべて Python 側で厳密に計算し、
`register_direct` で直接登録する（Core Principle #6 に一切触れない：どこにも
ルーティングしていない）。Maxima セッションでも Julia セッションでも同じ。

**ただし結果は行き止まりにしない**のが要点：

- 係数の canonical は CAS 値（`sqrt(6)/3`）
- 合成の恒等式の canonical は **J を記号に残した式**（`(J*(J+1)-15/4-3/4)/2`）

これで「両辺に A をかける」「F に値を代入する」といった**一般操作の連鎖**にそのまま
乗る。ランデの間隔則はこの連鎖で出る（`tests/test_angular_momentum.py`
`test_the_coupling_identity_composes_with_ordinary_cas_operations`）。

**物理はここで止める。** ハミルトニアンと結合定数は研究者が与える。F-9 が
`H_hf = A I·S` を仮定して準位を返すことはしない（feedback: no hardcoded modeling choices）。

### 展開の基底記号：利用者が決める、決めなければシステムが決める

非結合基底展開だけは「表示されているもの＝計算できるもの」が自明でない。ケットは CAS の
値ではないからで、当初これを**表示専用オブジェクト**として登録したところ、演算を掛けると
`UnknownNotationError: parser.unsupported_notation.pipe`（＝「パイプ記号は未対応」）が出た。
**黙って誤答は返らないが、何が起きたかも次に何をすべきかも分からない。** タイムラインに
出ているものは使えると考えるのが自然なので、これは設計の穴。

最終的な設計は次のとおり（設計判断は 2026-07-28 に利用者が決定）:

**積状態は常に名前付き関数として書く。** canonical は本物の式
`sqrt(2)/2*chi(1/2)*psi(-1/2) + …` になり、表示はそれを鏡写しにする
（`\chi\!\left(\frac{1}{2}\right)`）。**表示と計算可能物が一致する**ので、表示専用
オブジェクトはもう生じない。

**名前は利用者が決める。決めなければシステムが決める。**
- 指定あり →「… を u と v の非結合基底で展開して」。論文の記法に合わせられる。
- 指定なし → `_fresh_basis_names()` が未使用の記号を選ぶ。どれを使ったかは `message` で
  必ず伝える（利用者が頼んでいない選択なので、出力から逆算させてはいけない）。

**名前の検査**（`_check_basis_names_free`、何かを登録する前に実行）:

| 却下する場合 | 理由 |
|---|---|
| 既に使われている名前 | H-1 の定義は CAS 側にも束縛される（`phi : x^2`）。検査が無いと simplify が `(x^2)(1/2)` を含む式を **status=success で返した**。`chi`/`phi` は物理で最頻出の記号なので「起こりにくい事故」ではない |
| 2つが同名 | 第1・第2の角運動量は別の空間。同名にすると区別が消える |
| 添字付きの名前 | `chi_1(1/2)` は本プロジェクトの添字規則により `chi` の添字 `1(1/2)` として解釈される（実装中に自動生成名を `chi_1`/`chi_2` にして踏んだ）。ゆえに自動生成名も**添字を持たない別々のギリシャ文字**（`chi`, `psi`, `xi`, …）を順に使う |

照合先は `lhs_alias_map` / `SymbolContext.registry` / `bracket_functionals` /
**既存の展開が使った基底名**。

**残る限界（利用者向けドキュメントにも明記）:**
- 直交性は CAS が知らない（`chi(1/2)*chi(-1/2)` は 0 にならない）。内積・行列要素が要るなら
  係数を CG 係数として個別に求める。
- **逆向き（展開を作った後で同じ名前を定義する）は防いでいない。** H-1 の定義は設計上
  全体に伝播する（CLAUDE.md の P1/P2）ので、これは F-9 固有ではなくグローバル束縛の
  性質。F-9 側だけで塞ぐと H-1 の共有経路に F-9 都合の分岐を持ち込むことになるため、
  利用者向けドキュメントで「後で使う予定のない記号を選ぶ」と明記するに留めた。
- ケット表示（`|½,½⟩`）そのものは失われた。表示とcanonical の一致を優先したため。両立
  させるなら R-9 の `bracket_functionals`（`E[X]` を表示し `cas_name(args)` を CAS に渡す
  仕組み）にケットを載せるのが筋——未着手項目として記録。

**`_reject_display_only_operands()`** は残してある。`angular_descriptor["cas_usable"]` が
False のものを `run_operation` のパーサ手前で止める不変条件チェックで、現在これを False に
する生成経路は無い（＝上の設計がその状態を作らない）が、「表示されているのに計算できない
もの」が再び現れたときに**沈黙ではなく説明で落ちる**ことを保証する。

### `Expression.angular_descriptor`

`lattice_descriptor` / `integral_descriptor` に倣った provenance 用フィールド。ただし
**遅延計算は持たない**（値はもう厳密に確定している）。量子数が何を意味していたかを
記録するのが役目で、登録済みの式から後続操作（合成 → その J1·J2 固有値、など）を
起こす余地を残すためにある。

### `register_direct`（共有化）

`engine_deferred_forms_mixin.py` には「id 確保 → Expression 構築 → step 記録 →
head 前進」という同一構造が既に4箇所あった。F-9 で5つ目を作る代わりに
`register_direct(latex, canonical=None, **descriptor_fields)` に括り出し、
`register_bond_sum` / `register_integral_form` / `register_dispersion` /
`evaluate_integral_form` をそこに委譲した（約90行削減、フルスイートで挙動不変を確認）。

## 5. 設計判断4：LLM に投げない

6つのトリガーはすべて `ui/interpret_angular.py` のルールベース。schema 操作としては
登録していない。

理由は BP-6：必須フィールドが4個以上の操作でローカル Supervisor はフィールド抽出を
安定して誤る。CG は量子数6個、9j は9個。しかも**量子数を1つ取り違えた結果は、
もっともらしい値としてどこにもエラーを出さずに出てくる** — このノートブックで最悪の
故障モード。だから決定論的に読み、読めなければ**推測せず素通りする**。

### パターンは「トリガーのみ」を照合する

`i18n/nl_patterns.json` の F-9 エントリはトリガー句だけを見る。量子数は
`ui/interpret_angular.py` の `key=value` スキャナが**命令文全体から**拾う。

これは実装中に踏んだ問題への対処でもある。当初 args を正規表現でまとめて捕まえて
いたが、日本語の「j1=1/2, j2=1/2 **の** J=1, M=0 の状態を…」では助詞が量子数列を
分断して `J`, `M` を取り落とした。トリガーと数値抽出を分けたことで語順非依存になり、
日英で同じコードが動く。

### 発火順（`ui/interpret_pipeline.py`）

```
angular_wigner_symbol   ← 最も字義的（"3j記号 (…)"）。他と語を共有しない
angular_clebsch_gordan
angular_coupled_state   ← angular_couple より前（同一文に「合成」が出うる）
angular_couple
angular_wigner_eckart
angular_lande_g         ← 最後。JP パターンが最も緩い（"<何か> の g 因子"）
```

`coupled_state` のトリガーは**「非結合基底」「uncoupled basis」という語を必須**にして
ある。これが無いと汎用の `展開`（expand）操作を横取りしてしまう
（`test_unrelated_instructions_fall_through` が回帰を止める）。

## 6. 検証方法

**恒久テストは数学的恒等式ベース**（`tests/test_angular_momentum.py`）。外部ライブラリ
に依存しないので、どのマシンでも走る。

- 3j 直交性（m3 固定で m1 を走らせる — 関係式は δ_{m3 m3'} を含む）
- 3j 対称性：巡回置換で不変／奇置換と全 m 反転で位相 `(-1)^(j1+j2+j3)`
- CG 規格化（列の正規直交性）
- 6j 直交性
- **9j の 0 引数還元 → 6j**（9j 実装の独立検証として効く）
- 9j 転置対称性（位相 `(-1)^S`）
- 合成：`Σ(2J+1) = (2j1+1)(2j2+1)`（次元数の一致）、間隔則
- Wigner-Eckart：幾何因子の二乗和が 1

その上に**公表テーブル値**の層を置く（恒等式だけでは大域的な位相規約の誤りを捕まえ
られないため）：一重項/三重項、`⟨1 0 1 0|2 0⟩ = √(2/3)`、`{1 1 1;1 1 1} = 1/6`、
`g_J(^2P_{3/2}) = 4/3` など。

**開発時のみ** sympy と全数照合した（Julia 側 Conda の Python を読み取り専用で借用、
インストールなし）：3j 1642件・CG 2408件・6j 15625件・非ゼロ 9j 245件、**全一致**。
この照合はスイートには含めない（sympy はアプリの依存ではない）。
