# 33. 時間依存演算子とグリーン関数 — 記法か操作か（調査記録）

**日付:** 2026-07-30
**発端:** [open_items](../../KNOWN_ISSUES.md) の AUDIT-INDEXED-CALL（多重添字の量に引数を
付けた形）の設計判断を詰める議論。途中で**利用者の本当の目的がグリーン関数**だと
分かり、そこから問題の立て方自体が変わった。

**この文書の位置づけ。** 調査記録＋第1段の実施記録。ここに書いてあることの大半は
実測であり、結論は「何を作るか」ではなく「**何を作らないか**」を含む。

**第1段は 2026-07-31 に実装済み**（多重添字の適用形 → Maxima の subscripted
function。§2.3・§10）。**時間依存演算子（§5〜§7）は未着手** — 着手する人は
§5 の結論と §6 の限界、とくに §6.2 の「2種類の打ち切り」を先に読むこと。

## 1. 出発点 — 利用者が書きたい4つの形

議論は「多重添字＋引数をどう表すか」という記法の問題として始まった。利用者の
言い方を借りれば、書きたいのはこれだけである。

```
A_i          B_{i,j}          C_i(x)          D_{i,j}(x)
```

CAS の内部表現には拘らない。実測（2026-07-30、Maxima・未宣言）:

| 形 | 結果 | |
|---|---|---|
| `A_i` | `A(i)` | ○ |
| `B_{i,j}` | `B(i, j)` | ○ |
| `C_i(x)` | `C_i(x)` | **通るが添字が死ぬ** |
| `D_{i,j}(x)` | 拒否 | ✗ |

`C_i(x)` の「死ぬ」は具体的にはこうである。

```
subst(i=1, C_i(x))   →  C_i(x)     ← 何も起きない（C_i は名前）
subst(i=1, C(i)(x))  →  C(1)(x)
subst(i=1, Ci (reference omitted from the public snapshot))  →  C1 (reference omitted from the public snapshot)
```

つまり現状は「`D` は目に見えて拒否、`C` は**黙って添字が溶ける**」。後者の方が
性質が悪い。ただしこれは事故ではなく決定である（CLAUDE.md「A subscript that is
APPLIED is part of the name」）。理由は曖昧性:

- `bessel_j(0,x)` — `j` は**関数名の一部**（第1種ベッセル関数）
- `C_i(x)` — `i` は**添字**（第 i 成分の関数）

綴りが同じ `<名前>_<1文字>(引数)` で、宣言なしには区別できない。現状は
`bessel_j` を優先している。

## 2. 起票時の前提が2つとも実測で偽だった

open_items の AUDIT-INDEXED-CALL は「どう表すか」が未解決だとして、根拠を2つ
挙げていた。両方とも**測ると成り立たなかった**。

### 2.1 「IR に『添字付き量への適用』ノードが無い」→ ある

```python
FunctionCall(func=IndexedSymbol(base=Symbol("M"), indices=[i, j]), args=[x])
```

これは構築でき、**両バックエンドのコード生成器が既に歩ける**。止めているのは
リゾルバの拒否だけだった。

### 2.2 「既定の `function_call` では `M(i,j)(x)` になり不正」→ Maxima は受け付ける

実 Maxima で両形を比較した。

| 検査 | 配列形 `Mi,j (reference omitted from the public snapshot)` | 入れ子形 `M(i,j)(x)` |
|---|---|---|
| `tex1`（表示） | **`M_{i,j}(x)`** ← 利用者の記法 | `M\left(i , j\right)(x)` ← CAS 書式 |
| `diff` / `subst x=2` | ○ | ○ |
| `subst i=1` | `M1,j (reference omitted from the public snapshot)` | `M(1,j)(x)` |
| 同項の収集 | `2*Mi,j (reference omitted from the public snapshot)` | `2*M(i,j)(x)` |
| 添字ごとに別物か | ○ | ○ |
| `sum(Gi,1 (reference omitted from the public snapshot), i, 1, 3)` | `6*x+3` | — |
| 未宣言での副作用 | **無し**（`arrays` は `[]` のまま＝ハッシュ配列を作らない） | 無し |
| **表示を入力欄に戻すと** | `g_{mu,nu}(x)` ← 通る | **`M(i , j)*(x)` ← 積に化ける** |

不正なのではなく、**入れ子形は表示が利用者のものでなく、往復も壊れる**。
最後の行が決定的で、入れ子形は
[AUDIT-DERIV-DISPLAY-RT](../../KNOWN_ISSUES.md)（同日に根治した「表示→写し戻し→積」）
と**同じ壊れ方を新しく作る**。

配列形の `tex1` がコンマ区切り `g_{\mu,\nu}(x)` を返すのは偶然ではなく、
AUDIT-SUBSCRIPT-SPLIT が入力側に定めた「多重添字はコンマかスペースで区切る」
規則と**一致している**。表示と入力規則が同じ綴りになる。

### 2.3 したがって (b) の中身は「受け入れるか」ではない

**適用形については宣言に lowering を選ばせるのをやめ、常に配列形にする**か、である。
そうすれば宣言済み／未宣言の区別が消え、表示ブリッジも要らない。

**代償は1添字と n添字で挙動が割れること。**

```
A_\mu(x)       → A_mu(x)        名前に畳む。μ に代入できない
g_{\mu\nu}(x)  → gmu,nu (reference omitted from the public snapshot)    添字構造が残る。μ に代入できる
```

出口は2つあった。①割れを受け入れる。②1添字の決定も見直す。**②を実験して測った
結果、①に決まった**（下）。

### 2.4 ②を実測して却下 — 単一添字を添字にすると意味が壊れる

②（既定を反転して1添字も添字にする）を実装し、全体スイートで測った:
**24 failed / 3419 passed**。内訳のうち19件は「拒否される」ことを固定していた
テストで想定内だったが、**2件が本質的**だった。

- `my_func(x)` → `myfunc (reference omitted from the public snapshot)`。**宣言済み**の関数を添字アクセスにしていた。
  登録簿を見るように直して解消（裸の経路は元々登録簿を見ているので、揃えただけ）。
- `p_x(x)` / `p_y(y)` → **どちらも `p1 (reference omitted from the public snapshot)` に潰れる**。相互情報量の
  `p_x` の `x` は「どちらの周辺分布か」という**ラベル**、引数の `x` は**変数**。
  添字を代入可能にしたことで `x=1` がラベルまで書き換え、x の周辺分布と y の
  周辺分布が同一物になった。エラーは出ない。

```
subst([x=1,y=1], px (reference omitted from the public snapshot)*py (reference omitted from the public snapshot))  →  p1 (reference omitted from the public snapshot)^2        ← 意味が壊れる
subst([x=1,y=1], p_x(x)*p_y(y))    →  p_x(1)*p_y(1)    ← 従来（正しい）
```

`p_xy(x,y)` は宣言もされず組み込みでもないので、登録簿でも関数族リストでも
救えない。**単一添字には判別材料が無い。**

### 2.5 決まった線 — 添字が2個以上

**ラベルを区切って書く人はいない**（同時分布を `p_{x,y}` とは書かない）ので、
区切られた添字は曖昧さなく添字である。しかも多重添字はそれまで全部拒否されて
いたので、通しても壊れるものが無い。この線で測り直すと
**8 failed / 3435 passed**、うち6件は「拒否」を固定していたテスト、
2件はハイジーン上限と別件（利用者が置いた資料ファイル）だった。
**既存の正しい動作を壊したものはゼロ。**

単一添字は畳んだまま据え置き。判別材料が増えたら再訪する（§9）。

## 3. Julia は適用形を表現できない（バックエンド能力の問題）

```
f(_QA.QuIndex("i"), _QA.QuIndex("s"))(k)
  → MethodError: objects of type QuExpr are not callable
```

QuantumAlgebra の演算子は添字をいくつでも取れる（`a(is)`）。**ダメなのは結果の
QuExpr を呼び出すこと**なので、添字の数は関係ない。添字1個でも同じ:

```
a_i         → a(QuIndex("i"))                 実行 OK
a_{i,s}     → a(QuIndex("i"), QuIndex("s"))   実行 OK   ← 複数添字は問題なし
a_i(k)      → a_i(k)                          実行 NG   ← Sym a_i is not callable
a_{i,s}(k)  → 拒否
```

したがって「1添字関数ならよい」は成り立たない。**Julia で使えるのは『添字だけ』で、
それは1個でも複数でもよい。**

これは (b) を実装する場合の必須条件を意味する: 共有リゾルバが通すようになるので、
**Julia 側にバックエンドフックが要る**（Phase 2 の `_square_bracket_role` と同じ形。
各リゾルバが「適用された添字付き量を表現できるか」を宣言する）。

## 4. 却下した案 — 引数を添字に畳む

利用者案: `a_{i,s}(k)` を `a_{i,s,k}` として Julia に渡せば解決しないか。

構造的には通る（`f(isk)`, latex `{f}_{isk}`）。だが**代数を測ると却下**になった。

```
normal_form( f(i)   f†(j)   )  →  δ(ij) - f†(j) f(i)
normal_form( f(isk) f†(isl) )  →  δ(kl) - f†(isl) f(isk)    ← 第3スロットにも δ
```

QA は畳んだスロットに**完全な添字代数**を与える。よって:

- `(k)` が**量子数**（運動量・モード）なら畳むのは正しい。`δ(kl)` はまさに正準
  反交換関係であり、物理でも `a_{k\sigma}` と書く。
- `(t)` が**ハイゼンベルク描像の時間**なら畳むのは誤り。`{c(t₁), c†(t₂)} = δ(t₁t₂)`
  が出るが、異なる時刻の演算子はそう反交換しない。**エラーは出ず、もっともらしい
  誤答**になる。

そして `a_{i,\sigma}(k)` と `c_{k\sigma}(t)` は綴りが同じ形で、区別できない。

**決定的な非対称:** 量子数の場合、利用者は既に `a_{i,s,k}` と書けて、それは動く
（実測: `normal_order` → `a(isk)`、表示 `{a}_{isk}`）。**畳み込みは「既に正しく
書ける方」を便利にするだけで、「他に書きようがない方」（時間引数）では黙って誤る。**
利益と危険が逆向きに付いている。

副次的な壁も2つ測った。QA の**添字名は1文字必須**（`k1` / `k+q` / `omega` は
`ArgumentError`。`k+q` 系は既存の SymPy ルーティングが拾う）。表示は `{a}_{isk}` で、
利用者が書いた `a_{i,\sigma}(k)` と違ううえ添字の区切りも消える。

## 5. 立て方が変わった — 記法ではなく操作

ここで利用者が本当の目的（**グリーン関数**）と、決定的な指摘を出した。

> ハイゼンベルク描像や相互作用描像の演算子は、演算子の両側に指数関数が掛けられた
> 形で定義されている。定義に忠実に定式化すると、どうなるかな？

これで問題が消える。`c_i(t)` は**新しい種類のオブジェクトではなく、QA が既に表せる
演算子の積**だからである。

$$A(t)=e^{iHt}Ae^{-iHt}=\sum_n \frac{(it)^n}{n!}\,\mathrm{ad}_H^n(A)\quad\text{(Hadamard)}$$

実測:

| 測ったこと | 結果 |
|---|---|
| `exp(::QuExpr)` | **無い**（`MethodError`）→ サンドイッチの直書きは不可 |
| 対角 `H₀ = ε c†c` | `ad¹(c) = -ε c`, `ad²(c) = ε² c` ← 固有演算子、閉じる |
| 非対角 `H₀ = w(c†₁c₂+c†₂c₁)` | `ad¹(c₁) = -w c₂`, `ad²(c₁) = w² c₁` ← 張る空間で閉じる |
| 相互作用 `U n₁n₂` | `ad¹ = U c†₂c₁c₂`, `ad² = -U² c†₂c₁c₂`（原子極限では閉じる） |
| 異時刻反交換子（1次まで） | `1 - i·ε·(t-t') + O(2)` ← **δ ではなく本物の級数** |

最後の行が §4 の却下と対になる。畳み込み案なら `δ(t,t')` になっていたものが、
定義に忠実な形では正しい級数として出る。

**設計としての帰結:**

```
heisenberg_operator(A, H, t, order=N)   →  Σ (it)^n/n! · ad_H^n(A)
```

結果は**普通の QuExpr** なので、既存の操作（`normal_order` / `wick_contract` /
`substitute`）がそのまま乗る。新しいオブジェクト種も、新しい記法も、表示ブリッジも
要らない。**そして (c)（`a_{i,\sigma}(k)` に記法を与えること）は不要になる** —
拒否のままでよい。

## 6. 限界と、混同してはいけない2つの打ち切り

### 6.1 スカラー側は QA では持てない

`exp(-im*eps*t) * c(1)` は通るが、QA は c-number を分解する:

```
(exp(0)*cos(-eps*t) + abs(exp(0)*sin(-eps*t))i) c(1)
```

`e^{-i\varepsilon t}` のまま保持されず、`exp(0)` の残骸まで付く。グリーン関数の
結果としては読めない。したがって**係数と再総和は QA の外**（SymPy/Maxima）に
出す必要がある。これは CLAUDE.md の「QA → SymPy は一方通行」と
[BP-2](../../KNOWN_ISSUES.md) / BP-4 の領分そのもので、新しい制約ではない。

| 担当 | 内容 |
|---|---|
| **QA** | `ad_H^n(A)` の入れ子交換子（実測で正確） |
| **SymPy / Maxima** | `(it)^n/n!` 係数、`e^{i\lambda t}` への再総和、松原和・解析接続 |

### 6.2 「指数関数の打ち切り」は2種類ある — 混ぜると周波数空間に行けない

| | 小パラメータ | 正体 |
|---|---|---|
| Hadamard 級数を `t` で打ち切る | `Ht` | **短時間展開**。摂動論ではない |
| Dyson 級数を `V` で打ち切る | 結合定数 | **摂動論** |

相互作用描像が存在する理由がこの分離である。

$$A_I(t)=\underbrace{e^{iH_0t}Ae^{-iH_0t}}_{\text{厳密}},\qquad
S=\underbrace{T\exp\!\left(-i\!\int\! V_I\,dt\right)}_{V\ \text{で展開}}$$

`H_0` は二次形式なので `ad_{H_0}` は必ず閉じる（§5 の実測: 対角ならスカラー指数、
非対角ならモード添字上の行列指数）。**再総和は最適化ではなく必須**である:

```
∫dt e^{iωt} e^{-iεt}          = 2πδ(ω-ε)      ✓
∫dt e^{iωt} (1 - iεt + …)     項ごとに発散      ✗
```

`t` で打ち切った瞬間 `G(ω)` に行けない。**もし「指数関数を `t` で打ち切る」操作を
素直に提供したら、もっともらしい式が出て、その後の Fourier 変換だけが静かに
無意味になる。** 本プロジェクトが繰り返し潰してきた失敗の形なので、この操作は
**「閉じたら再総和、閉じなければ理由付きで断る」**にすべきである。

## 7. 既存資産との対応（着手する人向け）

| 段階 | 扱い | 現状 |
|---|---|---|
| `A_I(t) = e^{iH_0t}Ae^{-iH_0t}` | **厳密**（固有演算子→スカラー／行列指数） | 未実装。`commutator` の連鎖で成立することは実測済み |
| `S = T\exp(-i\int V_I)` | **結合定数で打ち切り** | **C-Ext-4 未着手**（`expand_perturbation_series`、Dyson 級数の自動生成） |
| `T[V_I(t_1)\cdots]` → 自由伝播関数の積 | Wick の定理 | **A-7 実装済み**（`wick_contract`） |
| 周波数空間・松原和・解析接続 | スカラー CAS | Maxima ✓（`residue`/`partfrac`/`sum` 実測済み）/ Julia は **BP-2** |

`extract_order` / `truncate_series` は「変数の冪で抽出／打ち切り」なので**結合定数用に
そのまま使える**。`t` での打ち切りに使ってはいけない（§6.2）。

**バックエンド選択の含意。** `(k, i\omega_n)` 空間のグリーン関数代数はスカラー CAS の
仕事で、留数・部分分数・和は Maxima にしかない。凝縮系ドメインの既定は Julia で
バックエンドはセッション作成時に固定（Core Principle #6）なので、**松原グリーン関数の
代数をやるなら Maxima セッションを選ぶのが現状の正解**、演算子代数（Wick 収縮・
正規順序）が要る局面だけ Julia、という切り分けになる。これは BP-2 が言っていることの
別の言い方である。

## 8. この議論で直したもの（記法側の副産物）

設計判断を要しない**バグ**が2件見つかり、その場で根治した。どちらも
「規則を2箇所に書くと片方が古くなる」形で、
[AUDIT-SHARED-CAS-LEAK](../../KNOWN_ISSUES.md) と同型である。

1. **無区切り添字の誤拒否。** `A_{ij}(x)` / `T_{ijk}(x)` が拒否されていた。適用形の
   分岐が添字分割規則を**再掲**していたため、同日の AUDIT-SUBSCRIPT-SPLIT
   （「無区切りは1添字」）に取り残されていた。`_parse_indices_from_symbol` を
   **呼ぶ**ように直して解消。
2. **裸の数字添字。** `G_0(k, omega)` が拒否される一方 `G_{0}(k, omega)` は通っていた
   ——**同じ量の2つの綴りが違う答えを出していた**。裸の分岐が
   `isinstance(_callee, Symbol)` を見ており、数字は `Number` としてトークン化される
   ため。アーカイブの **SUBST-DIGIT-SUB**（2026-07-05）と同じトークン化。3つの綴り
   （裸シンボル・裸数字・中括弧）の名前読み取りを `build_sub_name` に一本化して解消。
   `G_0` / `H_0` / `E_0` / `omega_0` に引数を付けた形は多体論の基礎語彙である。
3. **その出口側。** 2 で入口が通るようになった直後に測ると、**出口が壊れていた**。
   表示された `G_{0}\left(k , \omega\right)` を入力欄に戻すと `G_0*(k , omega)`
   ——積に化ける。`latex_converter._implicit_multiplication` の「数字のあとの `(`
   は積」規則（`2(x+1)` → `2*(x+1)` 用）が、数字が識別子の一部かどうかを見ずに
   **名前の末尾の数字**に当たっていた。数字の並び全体に `(?<![A-Za-z0-9_])` の
   ガードを付けて根治（1桁だけ見ると `A_12(` の `2` に当たるので、並び全体に
   錨を打つ必要がある）。**和を展開すると必ず `A_{3}(x)` の形が出る**ので、
   `\sum_i A_i(x)B_i(x)` を扱う経路は最後の一歩がここで壊れていた。
   **入口だけ直して出口を見ないと半分しか直らない** — AUDIT-DERIV-DISPLAY-RT と
   同じ教訓を、その修正の当日にもう一度踏んだ。

`tests/test_indexed_function_call.py`。

### 9.1 第2段（和の束縛）が本命な理由

単一添字のうち、**和の中にあるもの**は推測なしで添字と確定できる。そして
そこが今いちばん実害のある場所である:

```
sum(A(i)*B(i),     i, 1, 3)  →  A(3)B(3)+A(2)B(2)+A(1)B(1)   ✓
sum(A_i(x)*B_i(x), i, 1, 3)  →  3*A_i(x)*B_i(x)              ✗ 電磁気の内積
```

**実装（2026-07-31）。** 予想どおり障害は1つだけだった: 3箇所の IndexSum 構築のうち
2箇所が**本体をダミー添字より先に**解決していた（`\sum_i` 前置形だけが元から
正しい順序）。順序を入れ替え、束縛名のスタック（和は入れ子になる）を
`BaseSemanticResolver._binding` として持ち、`subscript_policy` に渡す。

```
\sum_i A_i(x)*B_i(x)  →  sum(Ai (reference omitted from the public snapshot) * Bi (reference omitted from the public snapshot), i)
実 Maxima で 1..3 展開 →  A3 (reference omitted from the public snapshot)B3 (reference omitted from the public snapshot)+A2 (reference omitted from the public snapshot)B2 (reference omitted from the public snapshot)+A1 (reference omitted from the public snapshot)B1 (reference omitted from the public snapshot)
```

`\sum_i p_x(x)` は `sum(p_x(x), i)` のまま——束縛されているのは `i` であって
`x` ではないので、ラベルは守られる。

判別材料の在庫（実測）:

| 材料 | 判別できるもの | 状態 |
|---|---|---|
| 添字が2個以上 | `D_{i,j}(x)` → 添字 | **実装済み** |
| 登録簿にある | `my_func(x)` → 名前 | 使える（§2.4 で実証） |
| CAS 組み込み | `bessel_j(0,x)` → 名前 | **実装済み**（`backends/maxima.function_families.json`、124件）。第3段のダイアログが `bessel_j` に出ないために必要になった |
| **和に束縛されている** | `\sum_i A_i(x)B_i(x)` → 添字 | **実装済み** |
| 添字が引数にも現れる | `p_x(x)` → ラベル | **採らなかった**（`p_xy(x,y)` を救えない）。第3段のダイアログが代わりに拾う |

## 10. 第3段の実測（2026-07-31）

**着手前に測ると、単一添字は利用者が何を言っていても畳まれていた。** 基底を行列と
宣言しても、`index_lowering_style` を明示しても、`notation_usage` に記録があっても、
すべて無視されていた。つまり「訊く」以前に、**既に言われていることを使っていな
かった**。順序を先に直し、ダイアログはその最後に置いた（§9.1 の在庫表を参照）。

ダイアログが出るのは1件だけであることを実測で確認:

```
C_i(t)                訊く
bessel_j(0,x)         訊かない   CAS 関数族
G_0(k, omega)         訊かない   数字添字は既定の命名規則で確定
\sum_i A_i(x)*B_i(x)  訊かない   和が答えている
D_{i,j}(x)            訊かない   多重添字は曖昧でない
基底 C を宣言済み      訊かない
前に答えてある         訊かない
```

**ハイジーン・ラチェットが2度、置き場の誤りを指摘した。** 1度目は判別材料を
`semantic_resolver.py` に足したとき（分割の趣旨に反する——ポリシー側へ移して
上限を上げずに収まった）、2度目は判別リスト読み込みの `except Exception`
（`(OSError, ValueError, KeyError, TypeError)` に絞れた）。どちらも上限を
上げるより正しい対応だった。
